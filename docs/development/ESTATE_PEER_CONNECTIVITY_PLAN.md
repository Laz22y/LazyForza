# 地产赛事直连连通性改进计划

状态：P0–P4 的本轮实现已落地，纳入客户端 `1.5.4-alpha-4` 与房主组件 `0.6.0-r4`；自动验证见第 9 节，真实网关与多机验证待完成。本文面向开发者与 Coding Agent，不作为发行说明；发行状态以远端 Release 为准。

编写日期：2026-10-11。代码基线：客户端仓库 `081d086`；已发行预览版 `1.5.4-alpha-3`，对应房主组件 `0.6.0-r3`。第 2–7 节保留设计基线和验收目标；实际接口、取舍和验证范围以第 9 节及当前源码为准。

## 1. 目标与边界

在现有房主制、邀请代码和连接回执流程上，提高可直连环境的建连机会、路径稳定性和失败可诊断性。优先补充能单独交付和验证的能力，保留普通 TCP、反向 TCP、UDP／QUIC 的现有路径。

约束：

- 建房、寻址和比赛不依赖任何外部协调、发现、公共 IP 查询、STUN、TURN 或中继服务。人工交换邀请和回执仍承担初始信息交换。
- 可选端口映射只与用户本地网关交互，比赛数据仍在玩家和房主之间直连。默认关闭，用户主动启用；不代为打开路由器的全局 UPnP 设置，不自动修改系统防火墙。
- 只开放赛事通信端口。Web 总控继续仅供房主本机使用；不映射总控、FH6 遥测或任意其他服务端口。
- 保留 Windows 10／11 的普通及反向 TCP 路径。UDP／QUIC 按当前系统能力检测启用；不为其他操作系统增加实现。
- 保留房主证书固定、回执认证和防重放、房间密码、参与者恢复及可靠事件去重。地址可达不等于身份可信，探测成功不等于比赛加入成功。
- 不改变 RaceServer 权威比赛规则，不新增项目来解决重试或换路，不自动迁移房主。网络变化不能自行恢复暂停的比赛阶段。
- 不承诺所有网络可达。没有已知可达地址、有效映射或双向通信路径时，客户端不能凭空发现未知的外部端口。

本计划不包含外部 VPN 集成、WireGuard 替换、随机端口扫描、TCP 同时打开、NAT64 专项适配或由第三名玩家转发数据。这些不作为失败后的隐含回退。

当前编码：邀请支持读取 `LFZP1`／`LFZP2`／`LFZP3`，回执支持 `LFZR1`／`LFZR2`。邀请最长 1024 字符；回执有效期 10 分钟。`LFZR2` 的传输标志作用于整组候选，候选本身只有 IP 和端口，没有每个候选独立的 TCP／UDP 类型。

特别注意：开发前的 `PeerReverseJoin` 从 `udpReceipt.Candidates[0].Port` 获取本地 TCP 监听端口。加入外部映射候选后，外部端口可能不同于本地端口；必须先改为使用实际本地 socket 端口，不能继续从序列化候选反推绑定端口。

2026-10-09 的版本不匹配排查证明：完整的新格式邀请也可能被旧客户端报为损坏，错误发生在联网前。诊断包未包含该次实际邀请或直连路径事件，不能据此判断 NAT 类型。现有真实验证边界见 [VALIDATION_WITH_FH6.md](../../VALIDATION_WITH_FH6.md)；本计划没有新增实机通过结论。

## 3. Tailscale 思路的适用范围

Tailscale 使用地址发现、协调通道、双向 UDP 探测和持续选路，并在无法直连时使用中继。其“数据直连”不等于建立连接时完全不使用服务器。这里仅借鉴能够脱离外部服务的机制。[官方连接类型](https://tailscale.com/docs/reference/connection-types)

| 机制 | 本项目决策 |
| --- | --- |
| STUN 获取公网端点、协调服务交换信息、DERP 兜底 | 不引入；继续使用自包含代码和人工交换 |
| 本地网关 PCP／NAT-PMP／UPnP 映射 | 作为显式可选能力；不能把内层映射成功当成公网可达 |
| 多地址探测、保留同一 UDP socket | 保留已有基础，改进调度和成功路径管理 |
| 测量延迟、重新验证路径、映射重建 | 分阶段实现，先处理同一 UDP 隧道内换路 |
| 随机端口碰撞探测 | 不实施；所需前提、流量与状态开销不适合作为默认连接流程 |

机制参考：[NAT 穿透原理](https://tailscale.com/blog/how-nat-traversal-works)、[映射恢复与选路改进](https://tailscale.com/blog/nat-traversal-improvements-pt-1)。借鉴的是机制，不能套用其连通率或把其服务器支持下的效果写成本项目承诺。

## 4. 分阶段开发

顺序为 P0 → P1 → P2 → P3 → P4。每阶段独立验收；前一阶段未获得实机证据时，明确保留待验证项，不用增加下一阶段功能掩盖失败原因。

### P0：连接阶段与诊断

**目的：先能确定失败发生在哪里。** 不改变网络策略和编码格式。

- 将尝试划分为代码解析、能力检查、普通 TCP、等待回执、双向探测／反向 TCP、TLS／QUIC 握手、房主身份校验、赛事登录、已连接、恢复、结束。传输分支可以并发，不能用一个线性状态覆盖其他仍在运行的分支。
- 每次主动重试分配本地 attempt ID；记录角色、客户端／组件版本、代码格式、传输能力、阶段耗时、候选类型、尝试结果和终止原因。对端版本未得到时标为未知，不能根据代码前缀猜具体发行版本。
- 区分格式不支持、代码损坏、过期、房间代次不匹配、无候选、系统不支持 QUIC、连接超时、认证失败、用户取消。超时只记录观察结果，不直接判定防火墙或 NAT 类型。
- 复用有界缓冲；逐包记录改为阶段事件和计数汇总。直连事件拟上限 500 条、序列化上限 512 KiB，超出时保留尝试摘要并记录丢弃计数；这些是待实现的资源预算，不是当前能力。
- `.lfzdiag` 拟增加带独立 `formatVersion` 的可选直连段，纳入原有清单摘要。没有直连数据的旧包仍可读取；检查现有读取器对新增段的行为再决定是否需升级容器版本。未启动游戏、遥测模块关闭时也能导出连接诊断。
- 房主进程产生的诊断经当前用户命名管道汇总至客户端；使用有界批次或拉取快照，不阻塞接纳、赛事时钟或遥测接收。

隐私：使用本次导出范围内的候选别名和地址类别；保留地址族、传输、RTT、错误码等必要字段。不得写入完整邀请／回执、nonce、密钥、密码、恢复令牌、原始网络包、真实 IP、SSID、网卡名称、用户名或绝对用户路径。异常对象先提取允许字段，不能直接导出 `ToString()`。如需按地址关联，使用不导出的随机盐；不要用可枚举的裸 IP 哈希。公开记录仅描述抽象网络拓扑。

**验收：** 三类失败分别可定位为“解析前失败”“传输无响应”“身份校验失败”；取消不记为故障；导出在无遥测时可用，敏感测试标记不出现在产物中，长时间失败不造成缓冲无界增长。

### P1：可选本地网关端口映射

**目的：获得当前缺少的可分享外部端点。** 先落地房主侧，再复用同一映射模块支持加入端反向 TCP／UDP。

1. 只在用户启用后，对当前有效接口的本地网关进行有界发现。优先实现 PCP，再按协议响应回退 NAT-PMP；UPnP 作为同阶段的后续子项，独立验收。协议缺失或版本不支持可以回退，明确的策略拒绝不得通过轮换协议绕过。首期聚焦 IPv4 NAT 映射，IPv6 沿用现有路径，不自动申请 IPv6 防火墙开孔。
2. 映射对象来自已经绑定成功的赛事 socket，明确区分本地监听端口、外部端口、TCP／UDP、网关、接口、租约到期和网络代次。策略位于 `EstatePeer`，房主进程和加入流程各自拥有租约，不依赖 WPF 存活。
3. 优先请求 TCP、UDP 使用相同外部端口，但接受网关分配不同端口的事实。内部候选必须记录传输类型和来源；不得把请求端口当成已分配端口。
4. 首期保留 P3／R2 线格式：不同传输的外部端点可去重后纳入共享候选列表，仍由现有有界尝试和认证确认实际可用性。旧解析器可能对端点尝试不适用的传输，这是兼容成本，不得误报为已映射。保留每传输的本地映射状态；最多 8 个候选，给局域网、可用 IPv6 和映射端点留位置。若此方式不能在预算内有效工作，再评估第 5 节的格式升级。
5. 映射在旁路执行，不阻塞建房和本地加入。发布邀请／回执前完成有界等待，或在映射稍后完成时明确提示代码已更新；不能修改用户已经复制的代码含义。早期实现沿用显式刷新／重新交换流程，不冒充已经支持 P4 的在线地址更新。
6. 请求有限租约，按协议和网关返回值续租，监测网关 epoch 或重启迹象；失败时退避并保留其他路径。正常关闭、用户禁用和建房失败时释放自有映射；异常退出靠有限租期回收，不创建永久租约。不能覆盖或删除其他程序、手动配置的映射；无法确认租约归属时不做破坏性清理。
7. 网关返回私网或共享地址时标记“外部可达性未确认”；即使返回全局地址，也需对端实际握手确认。映射被拒绝、协议不支持、无网关或续租失败均不导致客户端退出，不自动尝试外部服务。

网关报文是非可信输入：核对接口、响应来源和请求匹配；PCP 核对 nonce。UPnP 描述和控制地址限于选定接口的本地网关范围，拒绝互联网重定向、代理和外部 XML 实体，限制响应大小与超时。网关返回的端点仍需通过既有邀请地址校验。

协议依据：[NAT-PMP RFC 6886](https://www.rfc-editor.org/rfc/rfc6886)、[PCP RFC 6887](https://www.rfc-editor.org/rfc/rfc6887)。实现时核对重传、租约、响应匹配和重启恢复的具体条款；不把两个协议统一成未经验证的固定重试算法。

**验收：** 支持与拒绝映射、不同 TCP／UDP 外部端口、部分成功、端口冲突、双层 NAT、网关重启、关闭／崩溃后的租约处理均有明确结果。映射成功后由另一台 Windows 设备完成真实加入，才记录该环境的收益；检查总控仍仅监听回环。

### P2：按阶段调度探测

**目的：在双方准备好时更快尝试，连接稳定后减少无效探测。**

- 保留同一有效回执和公网侧 UDP socket；重试不能换端口、丢弃回执秘密或重置防重放序号。
- 将等待、主动尝试、已连接、路径失效、停止分开管理。等待房主导入回执时保持低频探测；房主接纳或玩家点击继续时进入短时密集探测。首次收到有效挑战时可触发有界回应和验证，避免依赖双方同时点击或时钟完全同步。
- 稳定后降低备用路径频率，异常时恢复探索；有效业务流量是否可代替保活须按双向状态判断，不能仅因本机持续发送就认为对端仍可达。
- 统一限制每回执和全房间的探测数量、并发、重传与大小探测开销，公平调度多个成员。预算不得随候选数与成员数无约束相乘。
- 先用 P0 测得的基线决定间隔和预算，再固化到集中策略；不得为缩短测试时间而缩短产品握手期限。重传挑战保留原 token，有效回应不能因下一次调度提前作废。
- 调度间隔必须与路径新鲜度、挑战有效期、大小探测和失效判定一起调整。例如不能降低备用探测频率，却继续用原先短时间窗口把正常路径判为过期；也不能通过无限放宽窗口接受旧回应。

**验收：** 高 RTT、丢失首包、晚导入回执、同回执重试、取消及多成员竞争均能按预期结束；稳定期探测量较基线降低，慢路径无饥饿。时序策略使用可注入时钟验证，真实超时回归继续保留。

### P3：路径质量与有限换路

**目的：在多个已验证的 UDP 路径中持续使用合适路径。**

- 每条路径记录新鲜 RTT、连续超时、探测成功情况和验证时间。重传后无法明确归属的响应不用于精确 RTT 样本；使用滑动估计，不能由单次低延迟决定永久优先级。
- 初始连接仍优先尽快可用；后台比较其他已认证、双向验证的地址。性能切换要求足够新鲜样本、持续优势及冷却期；当前路径失效时允许优先恢复可用性。
- 先只支持现有 `PeerUdpPath` 内部的远端地址切换，保持本地 QUIC 适配端点和连接身份。切换后重新验证报文大小，不能沿用旧路径的大包成功结论。
- 不同时新增 TCP 与 QUIC 间的在线无缝迁移。跨传输恢复仍走现有赛事重连、恢复令牌和事件去重，另行验证后才能扩展。
- 路径验证必须先于业务流量切换；伪造来源、单向可达、旧探测重放不能改变选中路径。

**验收：** 慢路径先成功后出现稳定快路径时可切换；延迟轻微波动不反复换路；主路径失效可使用已验证备用路径；换路不造成重复车手、重复计圈或总控暴露。

### P4：网络变化与恢复

**目的：减少地址失效后的手工操作，同时保留失联时的明确恢复入口。**

- 订阅网络变化和系统恢复事件，去抖后重新取址、核对实际路由和映射。通知仅是重新检查的触发器，不直接代表断线；变化期间仍可用的连接继续服务。
- 用本地网络代次区分异步结果，过期的发现／续租／探测结果不得覆盖新状态。取消旧工作并释放对应自有资源；重新绑定只在原 socket 无法继续使用时进行。
- 已有认证连接仍存活时，才考虑在受保护的直连控制通道交换候选更新。消息需绑定房间、当前会话、代次及单调更新序号，有大小和速率限制；更新只提供待验证候选，不直接授予加入或管理权限。
- 在线候选更新是本阶段的协议设计门槛：先确定直连层消息、能力协商和重放边界，再实现传输。不能把自定义字段直接塞入赛事 WebSocket，或把当前只返回固定身份的接口当作已支持双向候选交换。
- 将“更新地址候选”和“刷新邀请以撤销旧邀请”分开。不得因自动网络通知不停增加邀请代次、破坏现有回执和参与者恢复；地址更新不得延长旧邀请或回执的授权期限。
- 双方完全失联且没有仍可达的已知地址时，显示重新交换代码的入口。不能在没有信息通道时承诺双方地址自动同步。旧客户端保留手工刷新流程。

**验收：** 网卡启停、地址更换、睡眠恢复、路由器重启和连续网络通知可恢复或明确要求新代码；迟到任务不能复活旧地址；项目、房间身份与权威事件保持一致。

## 5. 格式与组件兼容

连接能力、本机组件控制、赛事协议是三个独立契约，不要为了路径管理一起升级。

| 变化 | 兼容要求 |
| --- | --- |
| 诊断、调度、RTT 策略 | 优先仅改本地行为；不改变旧报文含义 |
| 把映射所得端点加入 P3／R2 | 保持原有校验、数量上限和传输尝试语义；测试外部端口不等于本地端口 |
| 每候选传输标记、在线候选交换或新增探测语义 | 先定义能力协商和新旧行为；旧二进制格式拒绝尾随数据，不能直接附加字段假定旧版会忽略 |
| 本机管道增加映射设置或诊断快照 | 明确可选字段默认值、未知命令行为和旧组件降级；不兼容时提升 `ControlVersion`，同步安装校验和签名清单 |
| 修改赛事消息或权威行为 | 才修改 RaceServer Schema，生成三端，并执行双服务端验证；本计划默认不需要 |

确需新邀请／回执格式时，先完成兼容矩阵再确定编号，不在本计划预占格式号。新客户端继续读取 P1／P2／P3、R1／R2；未知新格式和内容损坏分别提示。已发行旧客户端无法被新代码改变错误文案，因此新格式还必须在分享界面标明最低客户端版本，并提供真实可用的旧格式路径或明确说明不支持，不能用降级绕过认证。

组件维持“服务端版本-r组件修订”的版本规则。仅改房主适配时增加修订；只有实际更新封装的权威核心才变更服务端版本部分。需要新客户端能力的组件必须通过客户端版本范围与控制协议限制分发，测试“新客户端＋旧组件”和“旧客户端拒绝不兼容新组件”。加入方仍无需安装房主组件。

## 6. 界面与状态表达

- 普通加入仍是邀请、密码和身份信息。首屏只显示当前阶段、简短结果与下一步操作，不展示协议列表或大段诊断。
- “比赛与网络设置”保持折叠；新增一个默认关闭的“自动申请路由器端口映射”选项，附简短用途说明。映射不支持时保留手动地址入口，避免重复弹窗。
- 状态严格区分“本机监听就绪”“网关映射成功”“对端路径已验证”“已加入比赛”。不要将 IPv6 存在或本机自连显示为公网已连通。

- 连接详情默认收起，可查看脱敏路径摘要和导出诊断。所有状态支持中英文，沿用主界面视觉语言；窗口保持非置顶、非模态，后台重试不抢焦点。
