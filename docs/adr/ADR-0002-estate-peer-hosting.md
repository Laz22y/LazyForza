# ADR-0002：地产赛事实验性客户端直连

- 状态：TCP 与回执辅助 QUIC 实验实现；完整公网连接与真实 FH6 多机验证待完成
- 日期：2026-09-20
- 范围：Windows 客户端之间的地产赛事联机

## 目标与边界

提供房主创建房间、其他玩家输入邀请代码和密码加入的实验模式。房主客户端管理本机房主组件，承担赛事权威计算和连接接收，无需用户部署或配置独立 RaceServer。

本模式不访问官方或第三方房间目录、信令、STUN、TURN、公共地址查询、DHT 引导节点或穿透代理；不把 VPN 服务作为联机依赖。创建、加入、赛道传输和比赛运行仅依赖参与者设备与其现有网络。普通更新检查等应用功能与此模式隔离，验收时禁用，验证直连本身没有外部依赖。

必须存在参与者之间可达的网络路径。双方都处于不可映射的 NAT 后、没有共同可达的 IPv6 或局域网路径时，无法保证通信。软件不能绕过不允许入站的运营商、单位或路由器策略。

本功能同步 LazyForza 的计圈、排名、处罚、阶段和 HUD。它不建立 FH6 游戏本身的车队连接，也不代替游戏的多人服务。

## 当前可复用实现

- `EstateRaceModule` 使用 `ClientWebSocket`，已包含登录、心跳、重连、可靠圈完成与进站事件确认，以及 latest-wins 遥测队列。
- 描述、赛道下载、Logo 与 WebSocket 统一使用 `PeerConnection` 的固定公钥指纹、同源约束与直连传输；密码不跨源发送。
- `LazyForza.RaceServer.Core` 只依赖 Protocol，可作为房主权威引擎；复用其排名、阶段、处罚、离线恢复和持久化契约。
- 已有原生房间支持 12 名车手与 12 名 OB。实验模式沿用协议容量边界，但不据此宣称所有房主电脑与上行带宽都能稳定满员。
- 现有独立服务器模式继续使用原连接流程；实验入口由用户主动打开，只有创建房间才启动可选组件和监听器。

## 房主结构与传输

采用星形连接：每位玩家和 OB 仅连接房主，房主向成员发送权威快照；不要求所有玩家互连。房主自己也经过同一套身份、计圈和处罚逻辑。

常规路径使用 HTTPS / WSS over TCP；TCP 不可达时，支持 QUIC 的 Windows 11 客户端可以人工交换连接回执。回执指定玩家候选地址和一次性随机标识，房主添加后双方主动发 UDP。QUIC 提供 TLS 身份认证、可靠流、拥塞控制和丢包恢复，现有 HTTPS/WSS 在 QUIC 双向流中传输，因此描述、赛道和赛事消息使用同一可达路径。

UDP 外层适配器保持公开端口，MsQuic 使用内部回环端口；只转发已人工接纳的候选地址和随机标识，不提供任意目的地址代理。为了适应 IPv6 最小 MTU，外层按需将一个 QUIC 数据报拆成至多两片，限制重组数量、大小和期限；丢失交给 QUIC 恢复，不自制确认与重传协议。每房间最多 32 条 UDP 路径，回执有效十分钟，未连接过期项及长时间空闲项释放。没有 STUN 时无法推导未知 NAT 外部端口，回执不能保证 CGNAT 穿透。

TCP 可避免把 UDP 可用性作为必要条件，但丢包时存在队头阻塞。继续对遥测使用有界、latest-wins 队列；圈完成、维修完成、离开、管理命令和确认走优先可靠队列，限制每条消息及待确认事件数量。每个连接独立发送，慢成员不能拖慢整个房间。赛道文件使用单独 HTTPS 请求与并发、带宽上限。

网络适配层提供房间描述、赛道下载、建立连接和证书身份四项能力，供服务器模式与直连模式分别实现。不能只替换 WebSocket 地址而遗漏描述和文件下载的身份验证。

房主 Web 总控复用固定版本服务端的原始页面、路由和支持类，与玩家连接共用同一权威核心。总控使用独立回环监听器，校验 Host、Origin 和会话；客户端通过当前用户管道取得短时一次性浏览器入口。对玩家的 TCP／QUIC 入口不开放管理路由。OB 权限和普通车手权限继续区分。

## 邀请代码

短随机码本身不能在无目录的互联网中找到房主。连接凭据采用自包含 `LFZP2-<encoded payload>` 格式，同时兼容读取旧 `LFZP1`，包含：

- 独立格式版本、房间随机 ID 与邀请代次；
- 房主身份公钥指纹；
- 有上限的候选 IP 地址、端口、地址族与网络范围；
- 有效期和输入校验信息。

采用变长代次、共享端口和地址前缀压缩，保留完整 SHA-256 公钥指纹；回执复用相同地址编码，以房间和邀请代次绑定。限制总长度和候选数，优先复制粘贴；短房间编号只供核对。不注册系统 URL 协议，不自动打开代码内的任意 URL。

密码不写入邀请代码。代码中的校验信息只能检测损坏，不代替身份认证；TLS 对端必须匹配邀请中的公钥指纹，密码在校验成功后的加密连接中提交。分享代码是房主身份的初始信任渠道，不能抵抗整个邀请被替换。界面显示短房间编号，完整指纹在邀请代码内。

邀请会暴露其中的连接地址，默认不把完整代码、密码或恢复令牌写入日志。重开房间生成新房间 ID；刷新邀请递增代次并拒绝旧代码的新加入，已认证成员通过独立会话恢复。换公网地址或 IPv6 前缀后刷新代码；离线成员需要房主重新分享，不能假装旧代码仍可自动寻址。

只尝试邀请内至多 8 个 IP 候选，依赖系统路由，不扫描网段。首版不使用需要接口作用域的 IPv6 link-local 地址；接受 IPv4、IPv6 全局地址与 ULA。回环地址只用于房主内部连接，外部邀请拒绝回环、组播、未指定和 IPv4-mapped IPv6 目标。

## 建连与网络适配

1. 自动收集已启用、带网关的非回环／非 Tunnel 网卡地址；高级设置允许填写指定网卡或外部 IP 与端口。无网关的静态局域网可手动填写房主地址。
2. 启动 IPv4 / IPv6 监听，检测端口占用；监听成功不代表 Windows 或路由器防火墙允许外部入站。
3. 收集局域网地址与适用 IPv6 地址。全局 IPv6 地址的存在不等于对端可达，不仅凭地址前缀宣布公网可用。
4. 公网 IPv4 由用户填写；公网地址在路由器时，用户配置 TCP 端口映射，并填入外部端口。首版没有 UPnP、PCP 或 NAT-PMP 自动映射。
5. 客户端不更改路由器或防火墙规则。手动映射后仍须由其他设备测试；不能仅凭内层路由器配置推断上游 NAT 可达。
6. 不调用公网查 IP 或测速服务。无法确定外部地址、NAT 层数或策略时显示“未知”，不能从一个连接超时断言对方处于特定 NAT 类型。
7. 加入方解析并校验代码，对有限候选采用有界交错尝试；IPv6 不通后及时尝试 IPv4，避免串行等待全部超时。建立 TLS、核对身份和房间 ID 后，才发送密码或恢复凭据。
8. 成功加入后沿用现有赛事连接状态、心跳与 HUD。房主窗口显示已加入车手数量，不宣称公网已打通；本机回环连接不作为异地可达证明。

直连请求不使用系统 HTTP 代理或隐含的转发服务。现有 VPN 或策略路由仍会影响系统选择的实际网络路径，用户需自行核对；本实现不安装、启动或依赖 VPN。

### 网络环境矩阵

| 环境 | 连接条件与边界 |
| --- | --- |
| 同一普通局域网 | 尝试私网 IPv4 / 本地 IPv6；无需公网和路由器映射 |
| 访客 Wi-Fi、AP 隔离、不同 VLAN | 本地地址可能不可达；候选尝试有超时，不从超时单独断定隔离原因 |
| 双方具备可路由 IPv6 | 优先尝试 IPv6；仍需房主和路由器允许该入站端口 |
| 只有房主有 IPv6、玩家仅 IPv4 | 不能直接使用 IPv6；需要房主同时提供可达 IPv4 或更换网络 |
| 房主有公网 IPv4 | 房主设备直接持有地址时检查主机防火墙；公网地址在路由器时需端口映射 |
| 普通家庭 NAT，可自动或手动映射 | 使用映射后的外部地址和端口；保留内部候选处理同网访问 |
| 双重 NAT、光猫加路由器 | 各层均须形成可达路径；仅内层映射成功不能标记公网可达 |
| CGNAT / 共享地址、无映射权限 | 优先改用可达 IPv6；没有其他路径则不能作为可入站房主 |
| CGNAT 但运营商明确支持受控映射 | 仅在实际取得可达外部映射后使用；不把本地 UPnP 成功当成运营商支持 |
| 共享地址、受限入站、DS-Lite | 按实际 IPv4 / IPv6 路径判断；不根据网络名称承诺可用 |
| IPv6-only、NAT64、464XLAT | IPv6 对端优先；IPv4 兼容路径必须实测，不硬编码转换前缀或假定可入站 |
| 同路由器不支持 NAT hairpin | 直接尝试局域网候选；不能只用房主外部地址 |
| UDP 被限制 | 首版赛事链路为 TCP；公网 IPv4 需要时由用户手动配置路由器映射 |
| TCP 入站被封 | 可交换回执尝试双向 UDP／QUIC；UDP 同样被封或只允许代理时失败，不使用中继 |
| 企业策略、公共网络配置、防病毒软件拦截 | 提示本机检查项；不关闭防火墙，不自动放开全部端口或覆盖单位策略 |
| 已有 VPN、多网卡、重叠私网网段 | 可手动补充地址；实际出站路径由系统路由决定，必要时调整网络配置 |
| 地址变更、Wi-Fi 切换、睡眠、路由器重启 | 连接失效时恢复或暂停；刷新候选和邀请，旧地址不再标记有效 |
| 丢包、抖动、高 RTT、低上行、MTU 黑洞 | 显示降级状态，限制流量和超时；分别测试 TLS 握手、素材传输及长时间比赛 |
| 双方均无可入站路径且无共同局域网 | 不支持建立新连接；建议有可达路径的玩家担任房主或调整网络 |

矩阵覆盖主要故障类别，不代表能够枚举所有设备、运营商与安全产品组合。错误文案区分观察事实、推测原因和建议检查项。

回执辅助 UDP 是 TCP 失败后的显式补充步骤，不改变正常的邀请加密码流程。当前不实现 TCP 反向连接。

## 身份、数据与恢复

- 房主为权威节点，持有全部比赛数据；此模式不提供抵抗恶意房主作弊的保证。
- 使用操作系统与 .NET 支持的 TLS，房间身份密钥保存在用户数据目录并采用 Windows 用户级保护；不安装根证书，不使用全局“接受所有证书”回调。
- 密码仅保存加盐的派生验证值；保留错误密码限流、握手超时、消息上限和未认证连接容量限制。
- 赛道由房主直接提供，继续执行大小、清单、内容和摘要校验；素材请求需要授权且限制并发。Web 总控托管的赛道与 Logo 由同一房间提供，读取路径遵守固定身份与同源约束。
- 恢复令牌限定到房间 ID、房主身份和参与者角色，不能复用普通服务器模式或另一房间的令牌。
- 房主中断时，成员进入连接中断状态，暂停权威比赛推进。房主恢复并确认后沿用保存的比赛与阶段 ID，重传的可靠事件继续去重。
- 首版不自动迁移房主，不由成员自行选举后继续计时。后续迁移必须另立状态交接与防止双主的协议，不能仅把“服务器地址”改成另一台电脑。
- 比赛核心在重要事件及周期检查点保存原子状态。关闭房间时释放本机席位、断开成员并停止监听；房间身份和恢复状态由 Windows 用户级 DPAPI 保护，组件卸载保留项目。异常退出后由房主选择原项目恢复，再通过绿旗确认续赛。

## 界面流程

入口为地产赛事中的“直连房间（实验）”，与现有服务器连接并列。

**创建房间**：首次使用先安装房主组件，显示实际下载大小，支持在线下载或离线导入；安装完成后选择赛道和项目，填写房间名、密码。常用规则摘要就地显示，高级网络设置折叠。创建成功后显示邀请代码、“复制邀请”、当前成员与网络状态；未被异地客户端验证前不显示“公网已打通”。

**加入房间**：显示邀请代码、密码、显示名与 OB 选项。连接过程分为寻找并验证房主、同步赛道并加入两个状态；连接条件说明按需展开。

**房间内**：常用准备、阶段控制与成员列表沿用现有视觉规范。房主额外显示管理操作；其他成员不能凭持有邀请取得管理权限。

**连接失败**：保留用户输入，分别提示代码无效／过期、未找到可达房主或加入阶段返回的错误。不可达提示列出 IPv6、端口映射和防火墙检查项；不从超时单独断言密码错误或 NAT 类型。

## 代码归属与构建

轻量 `LazyForza.EstatePeer` 负责邀请格式、候选枚举、连接编排、身份校验及房主组件管理；WPF 窗口留在 App。独立 `LazyForza.EstatePeer.Host` 承载权威核心、Kestrel 与持久化。主客户端不引用 ASP.NET Core 或赛事权威引擎。Domain、Telemetry、Analysis 不增加对网络或 WPF 的反向依赖。

权威规则以 RaceServer Core 为唯一源。`scripts/Sync-EstatePeerEngine.ps1` 从干净的服务端提交生成固定版本 Core / Protocol 包，含未修改源码和 provenance 哈希；`vendor/estate-peer-engine` 是仓库内离线 NuGet 源，只供房主组件引用。普通构建无需并列服务端仓库，用户运行时不连接 NuGet。更新规则先修改双服务端并验证，再更新固定包，不能在客户端分叉规则实现。

房主组件使用 Kestrel，单独提供所需运行时，不要求用户额外安装 ASP.NET。证书、连接接收与房间初始化采用显式配置，不能继承生产服务器的数据目录、管理员密码或公开 Web 路由。

### 按需安装与体积

房主组件不进入默认客户端发行包，加入者无需下载。首次创建房间时用户明确选择安装，主页面仅显示一张紧凑的组件卡片；可查看已安装版本、占用空间和卸载操作，卸载程序文件保留比赛项目。

组件下载是软件分发，不参与联机寻址或通信。安装后创建、加入和比赛可在下载站不可达时运行。支持离线包导入；更新不在比赛中替换正在运行的组件。房主组件由 GitHub／GitCode 的 `Laz22y/LazyForza.Components` 仓库独立分发。

2026-09-20 的本地封装测量：未修改的 Core / Protocol DLL 合计 386,048 字节（约 377 KiB），含源码的两个依赖包合计 205,757 字节。本机 ASP.NET Core 9.0.20 共享运行时目录为 29,001,956 字节（约 27.7 MiB）。这些是可行性测量，不是最终分发包大小；独立自包含组件还可能包含 .NET 基础运行时，正式下载与安装大小必须测量完整产物后写入清单。

首个本地自包含组件 `0.1.0-experimental.1` 实测为 48,891,331 字节下载、107,628,407 字节安装（336 个文件），当时仅提供离线导入。当前组件大小以客户端内嵌或经签名验证的清单为准；默认客户端只增加轻量连接程序集、公钥与清单。

独立更新使用 ECDSA P-256 签名清单，声明客户端版本范围、稳定／预览通道、单调递增序列、有效期以及控制／赛事／项目格式版本。组件编号采用服务端版本和独立修订号，按两者依次比较；同一服务端的房主适配修复无需更改服务端版本。更新完整安装后先备份项目，再原子切换本地选择；可回到仍完整的上一组件，不覆盖比赛数据。已经验证的版本允许离线使用，发现新版本时必须验证清单有效期。

组件使用固定 ID、受信分发来源、版本兼容范围、文件清单与 SHA-256 校验，防止路径逃逸、解压膨胀和不完整安装；临时目录验证全部完成后再原子启用。客户端只启动已校验的指定入口，不扫描或执行任意插件 DLL。

客户端与房主组件通过仅当前 Windows 用户可访问的命名管道交换启动参数和管理命令；密码与密钥不放进命令行。客户端退出、主动关闭房间或管道断开时，组件保存状态并结束监听。外部玩家只能访问赛事端点，不能调用本机管理管道。

直连外层握手和邀请使用独立版本；能复用的赛事消息继续沿用协议 v2。若新增共享赛事 DTO，则通过 RaceServer Schema 生成三端并运行对应兼容测试，不能手写生成文件。

## 验证范围

已实现核心封装、固定指纹 TLS、回执辅助 QUIC、原生 Web 总控复用、可靠事件适配、受限管道、组件完整性校验／离线安装、创建／加入界面、邀请刷新和保存项目恢复。自动测试覆盖本机 TLS、UDP 中的赛道下载与完整模块加入、错误证书拒绝后继续服务、12 车手与 12 OB、恢复令牌隔离、项目启动失败回滚、总控会话与同源校验、组件进程退出与重开，以及中英文窗口布局。自包含组件经过本地进程验证。

路由器自动映射、TCP 反向连接、自动迁移房主尚未实现。跨网络双向原始 UDP 路径已有小范围检查结果；完整跨网 QUIC 加入、弱网、不同 DPI 和 FH6 联机仍待验证。本机容量测试不能证明满员真实比赛的性能。

真实网络验证应分别记录局域网与独立网络之间的 IPv4／IPv6、手动映射、双重 NAT 及不可达条件。联机进程的连接清单用于核对只联系参与者地址；隔离应用更新等其他功能后，再检查无外部服务依赖。房主同时运行 FH6 时，还需观察 CPU、内存、帧时间、上行与长时间比赛恢复。

可先使用独立诊断设备按[网络测试说明](../ESTATE_PEER_ROOMS.md#连接路径检查)检查 TCP／HTTPS 路径；这不证明房间认证、WebSocket 长连接或实际计圈。实测结果另行记录在 `VALIDATION_WITH_FH6.md`，不以同机、容器或 Simulator 结果替代。

## 依据

- [RFC 8445：ICE](https://www.rfc-editor.org/rfc/rfc8445.html)：候选收集、交换、连通性检查与服务器反射／中继候选的区分。本方案仅借鉴候选检查，不声称实现完整 ICE。
- [RFC 6887：PCP](https://www.rfc-editor.org/rfc/rfc6887.html)：网关端口映射及多层 NAT 的约束；映射不等于任意网络可达。
- [RFC 6598：共享 IPv4 地址空间](https://www.rfc-editor.org/rfc/rfc6598.html)：`100.64.0.0/10` 属于共享地址空间，不能直接当作公网候选。
- [Microsoft：Windows Firewall](https://learn.microsoft.com/windows/security/operating-system-security/network-security/windows-firewall/)：默认入站阻断与有范围的规则管理。
- [Microsoft：Kestrel endpoints](https://learn.microsoft.com/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-9.0)：嵌入式监听与 HTTPS 证书配置；实施时以仓库固定的 .NET 9 工具链核对。
